## C. Payment and access flows

| Situation | Behavior |
|---|---|
| Eligible new owner | Explicit card-trial choice uses a server-mapped three-day product. Only verified trial dates, recurring collection, matching workspace/customer and a valid single-use claim grant trial limits. Email/domain history is retained. A paid selection defaults to paid checkout. |
| Trial ended, canceled agreement | Preserve setup and records. Verify the prior agreement really is canceled and the previously covered period has ended. Read the customer's agreements before another checkout. Choose the **paid** variant of Starter, Growth or Scale; a used trial cannot prevent that purchase or silently create a second free trial. |
| Existing paid owner changes tier | Confirm target, terms, expected contract and current period end. Call `POST /v1/subscriptions/{id}/upgrade` on that same subscription with `update_behavior=proration-none`. Provider renewal product changes now; **no immediate prorated charge, credit or refund**. PlaneByte maintains the already-paid allowances until renewal; new allowances require a verified full payment for the new period. The contract ID is preserved; prior periods/usage are not reset. There is no automatic retry of an uncertain remote mutation. |
| Checkout pending/abandoned | Return and page refresh grant nothing. Resume a verified pending checkout, or check provider status. A provider-confirmed expired **checkout** permits a fresh session. Ambiguous creates without a provider ID require reconciliation; no repeated blind POST. |
| Failed renewal, `past_due`, `unpaid`, `expired`, paused | Premium work fails closed. A provider's `subscription.expired` is not proof that billing retries have ended. Do not create a competing agreement while Creem may retry. Owner can refresh or manage the existing agreement. Paid-through cancellation retains access only through the independently verified period. |
| Multiple historical agreements | Select the verified workspace/environment slot, not the newest arbitrary row. If a provider customer spans historical workspaces, opening its customer-wide portal could expose another workspace's records. Keep in-app billing history scoped and return an explicit review message for that portal. |
| Refund/dispute/late event | Existing signed event inbox and payment verification remain authoritative. A return URL, plan label, duplicated event or provider payment-page load is never proof of paid access. |

**Official references checked:** [Creem hosted checkout](https://docs.creem.io/features/checkout/checkout-api), [subscription management and proration](https://docs.creem.io/features/subscriptions/managing), [upgrade endpoint](https://docs.creem.io/api-reference/endpoint/upgrade-subscription), [customer subscriptions](https://docs.creem.io/api-reference/endpoint/list-customer-subscriptions), [webhooks and retry semantics](https://docs.creem.io/code/webhooks), [test mode](https://docs.creem.io/getting-started/test-mode). The three older `/skills/creem-api/…` URLs returned 404. The repository calls Creem REST v1 via `httpx`, not a separate billing SDK.
