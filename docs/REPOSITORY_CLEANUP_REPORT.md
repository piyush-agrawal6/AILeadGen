# Intent Radar backend retirement

## Payment and database retirement — subsequent execution

This section supersedes earlier Razorpay and inventory status below. The serving application was independently verified at `ba9b9bbff3da3d464608f514c095ca7e906c213f` on clean schema 1017. Migration 1018 has run on restored copies only. No production database or storage object has been deleted in this stage.

**Payments.** Removed the Razorpay network client, plan mappings/creation tooling, subscription state machine, verification, renewal polling and quota fallback. Old purchase, portal-adjacent verification, recovery and cancellation paths cannot create a charge or entitlement (410). Historical sandbox subscriptions/payments retain their original identifiers and are read-only. Creem remains the commercial checkout and settlement authority. The PayU purchase and callback tombstones remain 410. No live environment secret was changed.

A read-only query of the configured Razorpay Test Mode account returned two webhook registrations, one active and one disabled, both pointing to the production `/api/billing/webhooks/razorpay` URL. One subscription was cancelled; payment history had two captured and three failed payments, zero refunds. These are provider **test** records, not PlaneByte commercial payments. A signed receipt-only endpoint remains for that registration. It authenticates bounded raw bodies, rejects changed-body replay and neither dispatches reconciliation nor mutates payments or grants. Unenrolled subscription IDs are ignored. The protected older frontend files remain as compatibility consumers. No deregistration or live-money action was performed.

**Creem and audits.** The pre-existing real Test Mode Starter subscription (hashed identifier prefix `731c60c9cc`) reconciled, inherited access was checked in an explicitly attached QA workspace, and two authentic inbox-event replays left one checkout, one contract and one payment. Offline tests cover failures, cancellation, expiry and protected financial actions; this does not assert a new live purchase or refund. `pip-audit` checked 108 locked distributions with zero known vulnerabilities; npm production dependency audit found zero advisories. Including development dependencies produced nine moderate lint-toolchain findings.

**Database inventory.** Read-only, repeatable snapshots covered both configured database destinations, across all visible non-system schemas: 667 tables/partitions and 7,397 constraints on the current destination (including its acceptance schemas), and 467 tables/partitions and 4,064 constraints on the older destination. Index, FK direction/delete behavior, sequence, view, function, trigger, policy and grant inventories are stored privately beside the backup; the script `scripts/audit_database_retirement.py` records metadata and exact counts without row contents. The old `public` schema contains shared identities (2 users, 1 customer account, 2 workspaces), 141 audit records and 34 contacted-recipient records. Treating that database as an obsolete Lead Engine project would destroy shared or retention-sensitive data.

**1017 → 1018 rehearsal.** `retirement-1018-20261121T171520Z/production.dump` was checksummed and restored to a separate PostgreSQL database. Only the legacy prospecting router uses `discovery_searches` (not Intent Radar's `intent_discoveries`); no incoming FK or view depended on it. Its zero rows, 3 indexes, 2 outgoing FKs and the empty table were retired on the copy, using `DROP TABLE … RESTRICT`. Three disabled `organization_products` flags for literal `LEADGEN` were deleted; no membership or workspace was deleted. The Radar writer no longer inserts these flags. Migration rerun applied zero. All 147 other application tables retained identical counts and content digests; all remaining product rows were identical and the full target structure fingerprint matched. Negative tests cover a populated table and a dependent view: the entire migration must abort without losing even a disabled flag.

## Release boundaries

At audit time the live API was `leadengine-api-00218-yag` at 100%, worker generation 101, acquisition generation 56, schema 1017, frontend `dpl_6y9vp92nWqYxghbBNyCnGvs4XLky`. Only the Intent Radar dispatch schedule was enabled among the six inspected schedulers. Five legacy/delivery schedules were paused. `leadengine-quota-canary` also exists. A paused schedule or empty table is insufficient evidence that a provider has unregistered a callback. Cloud resource names do not establish which product code an operation uses.

The remaining Razorpay test transport, callback and protected client's subscription interfaces still need coordinated retirement: live API configuration contains Razorpay bindings and `BILLING_ENABLED=true`. No live secrets were read into this inventory or removed. Retained legacy-profile tests/clients still consume Lead Engine endpoints. The clean schema shares company profile, intelligence dispatch, roles, export and notification services with historic modules. Their removal needs compatibility verification beyond import counts. See `docs/PLANEBYTE_PRODUCTION_INTEGRATION.md` for the protected release process. Production rollback remains the serving shared-billing release and its tested 1017 bridge; linked-account operations may pause on the bridge. Do not reverse schema history.
