## Contract and coverage

`POST /api/intent-radar/exports/{csv|xlsx|json|pdf}` accepts `app/intent_radar/exports.py:Selection`. It takes **references and filters**, never customer-supplied rows, owner IDs or provider permissions. The API resolves the active organization/actor and checks product and access period. Rendering is separate from collection. Snapshot v1 includes dataset, typed identifiers, approved public fields, source permalink, observation/collection dates, optional attribution, and a SHA-256 content identity. Internal actor/workspace/selection are not downloaded in the file JSON envelope. `records` is a list, not a representation of the database row; private notes, grants, credentials, raw provider metadata and contact data are not selected for output.

| Dataset | Selection and behavior |
|---|---|
| Discovery | Owned run ID as `parent`, optionally a subset of its recorded signal IDs. Never infers membership from a shared keyword. |
| Signals | Current selected IDs, current page, or all matching the server-side signal view. |
| Opportunities | Owned opportunity IDs; exports status and current original signal evidence. All matching uses the same listing service and filters. |
| Monitoring | Owned monitor ID; exports linked matches, not scheduler credentials or all conversations from the source. |
| Saved research | Saved signal evidence, selected records or current collection/search. Synthetic local library summaries are not backend research reports. |
| Growth | One accessible, completed report with current evidence. New formats include research title, summary and cited records; existing detailed Markdown remains contextual. |

CSV uses UTF-8 BOM, CSV quoting and inert spreadsheet formula prefixes even after leading controls/whitespace. XLSX is a native workbook with a filter, frozen header and UTC date cells; cells Excel cannot represent are rejected. PDF uses ReportLab, escaped text and local PlaneByte branding. JSON preserves source text; copying summaries runs the same authorization and attribution path before writing to the clipboard. The file path uses a single bounded response: **at most 100 records and 500 KiB of snapshot JSON**. Oversize/empty/ineligible selections fail explicitly. File format does not increase permission. A destination can retain a downloaded file; local deletion cannot retract it.

Source checks default to deny. Hacker News requires a canonical permalink. Stack Exchange requires export permission and attribution including author, profile and license. Public GitHub requires repository identity and attribution; private-connected evidence is not transferable. Bluesky requires a public handle and attribution. Configured provider gates, source availability and the tighter workspace/provider retention apply. YouTube, Discourse and custom feed exports are not enabled by this change. Per-publisher feed export approval is a separate prerequisite. Do not interpret a restriction error as permission to export a cached browser row.

## Google Sheets

Entry: `/intent-radar/integrations/sheets` or the export dropdown. `/api/intent-radar/sheets` uses the existing encrypted Google grants, single-use workspace/actor-bound PKCE state and leased refresh logic. `app/integrations/radar_sheets.py` supplies the dataset adapter and `app/integrations/sheet_exports.py` performs the same fixed-range Google `values.update` with `valueInputOption=RAW` as the legacy worker. The new `radar_sheet_exports` table has no dependency on Lead Engine lists. It stores selection, digest, destination, range, creator, connection revision, expiry and job state rather than durable copies of discussion text. Existing sales-list exports remain on the old table.

1. Owner/admin explicitly requests `https://www.googleapis.com/auth/spreadsheets`; legacy read-only consent remains `https://www.googleapis.com/auth/spreadsheets.readonly`. No Drive listing, profile/email scope, automatic append, or continuous sync. The displayed identity is the authorizing **PlaneByte member**. The Google email address is not asserted. Choose an existing spreadsheet and inspect accessible worksheets. New spreadsheet creation is not offered.
2. Stage up to 100 eligible rows, inspect exact destination/range, column names, row count and preview; explicitly approve overwrite. At most 20 new reviews per workspace per hour, one-hour review lifetime. Request IDs deduplicate staging. Scope, ownership, revision, snapshot digest and retention are checked again before the worker writes. A changed result set needs a fresh review. The worker checks the provider's updated-cell count before marking success. An uncertain outcome needs explicit repeat approval to write the **same range**. Cancellation cannot retract an in-flight or completed provider write. The management screen exposes the most recent 25 reviews by the current actor and allows history refresh.
3. “Connected” requires the write scope, a connected record with no recorded error, and a successful spreadsheet read after this connection was established, within 15 minutes at the status read. Expired evidence means “Health Unknown”; a failed capability query is not positive health. Disconnect clears local authority. Separately revoke the Google grant if needed.

**Configuration:** existing `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, `HEYSOW_INTEGRATION_ENCRYPTION_KEY`, `HEYSOW_WORKSPACE_MANAGEMENT_ENABLED`, `HEYSOW_CUSTOMER_INTEGRATIONS_ENABLED`. Legacy `GOOGLE_SHEETS_REDIRECT_URI` stays intact. New production opt-in: `RADAR_GOOGLE_SHEETS_REDIRECT_URI=https://app.planebyte.com/intent-radar/integrations/sheets/callback`. Register this **additional** exact redirect on the existing web OAuth client. The historical `leads.planebyte.com/acquisition/sheets/callback` belongs to the legacy product: a browser test confirmed the acquisition route redirects when Lead Engine is disabled. Keep that registration; verify consent audience/app scope approval in Google Auth Platform, then set the Radar-specific URI. Local fixtures use the Radar route on their own localhost origin. Do not broaden Google login or Gmail grants. Existing executor uses `GCP_PROJECT_ID`, `GCP_REGION` and `LEADENGINE_CLOUD_RUN_JOB`/`CLOUD_RUN_JOB`.

## Webhook contract v1

Manage at `/intent-radar/integrations/webhooks`; advanced API/MCP keys stay in Settings → Developer & API. Reuses `/api/organization/webhooks`, `app/webhooks/service.py`, `dispatch.py`, `worker.py`, and the existing encrypted endpoint/outbox/attempt tables. Requires admin management, entitled Radar, positive `api_requests` for managed plans, `HEYSOW_WEBHOOKS_ENABLED`, vault key and new default-off `RADAR_WEBHOOK_EVENTS_ENABLED`. Enable the latter on both API and worker only after verifying the dedicated `webhooks-dispatch` job. A scheduler running `intent-radar-dispatch` alone is insufficient.

| Topic | Authoritative transition |
|---|---|
| `radar.signal.qualified` | A newly inserted eligible discussion passes the opportunity admission policy, or an explicit review actually changes status to Qualified. Ordinary mentions and rediscovery alone do not emit it. A later human qualification is a separate occurrence from original observation. |
| `radar.signal.status_changed` | Explicit single/bulk review changes a status other than entry into Qualified; notes-only or same-status updates are excluded. Implicit housekeeping changes are not advertised as reviews. |
| `radar.opportunity.created` | An eligible signal is promoted into its deterministic workspace opportunity, including bulk promotion. The status on creation is not a claim of verified purchase. |
| `radar.opportunity.status_changed` | Successful revision-checked edit changes opportunity stage; priority/notes-only edits are excluded. |

Envelope: `{schema_version:1, id, type, created_at, workspace_id, data:{signal_id OR opportunity_id}, resource}`. `resource` is a relative `/api/v1/intent-radar/...` path, never a bearer URL. Use a separately authorized `intent:read` credential to read current detail. Event insertion shares the domain transaction. The unique endpoint/event key suppresses repeat enqueues. Before sending, the worker checks endpoint authority, revision, subscription, current product entitlement and eligible evidence. The recipient gets no conversation body or credential in the event. Ordering is best-effort; retries may arrive after subsequent changes. Fetch current resource state rather than treating delivery order as a ledger of all intermediate values.

**Receiver verification:** read raw bytes before parsing JSON; require an integer `X-PlaneByte-Timestamp` within the receiver's chosen freshness window (e.g. five minutes); compute `v1=` + lowercase hex HMAC-SHA256(secret, ASCII timestamp + `.` + raw body), and constant-time compare with `X-PlaneByte-Signature`. Reject stale/invalid messages. Persist the event ID before side effects and acknowledge only durable acceptance. `X-PlaneByte-Event-ID`, `X-PlaneByte-Delivery-ID`, and `Idempotency-Key` support deduplication. At-least-once attempts, **not exactly once**; five attempts maximum per retry cycle. Public HTTPS, restricted port, pinned public DNS, redirects disabled, short timeouts, bounded backoff and no response-body logging are inherited. A permanent failure can pause the endpoint. Rotate secrets through the administrator view; save the new value at rotation.

**Generic recipes** (protocol instructions, not vendor acceptance):
- **Zapier:** use Webhooks by Zapier → Catch Raw Hook; subscribe its permitted HTTPS receiver or route through a signature-verifying receiver you control. Verify the signature and deduplicate before creating downstream records.
- **Make:** use Webhooks → Custom webhook, preserve headers/raw bytes for verification or send only verified messages from your receiver. Route by `type` and use the event ID as the data-store key.
- **n8n:** use a POST Webhook trigger with raw body and headers; verify before parsing, deduplicate in persistent storage, then branch by `type`. Do not put an API key in the webhook URL.
- **Custom receiver:** same signature/freshness procedure, durably enqueue, return a 2xx and read details through the authenticated resource if needed. If a vendor does not preserve raw bytes, verify in a controlled relay first. Native Zapier/Make/n8n apps remain Coming Soon.
