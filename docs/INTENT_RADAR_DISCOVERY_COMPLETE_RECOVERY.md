## Request lifecycle and findings

1. `CreateDiscoveryPage` used `/discover/copilot` but expected `proposal.patch`; the server returns typed actions with fields such as `configuration`. The browser read only the first proposal; on error it manufactured keywords and sounded like a successful AI response. The revised builder consumes the server-validated, versioned `/draft` SearchDraft instead. Its proposal includes the full configuration, name and objective. Only Apply writes it to the form; a changed draft invalidates the preview. Undo includes ICP. Provider failures retain the prompt and deterministic fallback is labeled.
2. The AI input itself failed before inference on a restored copy of the affected workspace. The source catalog alone serialized to **17,792 bytes**, approved feed metadata to 1,986, plus other context, exceeding the 20 KB bound. After removing presentation metadata a second independent limit became visible: daily 100,000-token ceiling, 71,252 already reserved, proposed reservation 29,574. Dropping unrelated recent run history from the actual prompt reduced the real request, without changing either limit. An uncached AI-assisted CRM setup then returned in **6.1 s** with five keywords and four exclusions. It did not produce specific phrases or categories on that sample. Execution of the approved draft was **partial**. This is evidence of successful generation and application-level execution, not a claim of perfect quality.
3. `/capabilities` calls `connectors.catalog`; `/sources/configurations` returns workspace-scoped approved IDs. The old create page substituted hardcoded configured cards when the catalog was absent and hid the configuration control for Atom and Discourse. The builder now uses the fetched catalog, exposes the existing source editor, requires approved IDs of each selected feed family and removes deselected families' IDs. `POST /discover/preflight` runs the same `Search` schema and `connectors.validate` as creation, without reserving or dispatching. Creation/worker independently recheck. No generic RSS row exists for the owner; Atom and Discourse have ten enabled rows each. All three use the same bounded feed transport/parser, with distinct approval lists.
4. `Search.semantic` really requires `offerings`: the engine retains candidates then evaluates bounded, cited analyses. The builder exposes an editable offering and blocks missing input before submission. Keyword search remains explicit. Automatic profile offering selection is not yet qualified.
5. `/discover` → `discovery.create` reserves under the stable discovery ID, persists `intent_discoveries` and metadata, then creates an `INTENT_DISCOVER` job. `dispatch.launch` sends it to the existing worker. `jobs._execute` checks actor and lease; `discovery.process` fetches providers, normalizes, classifies, deduplicates and checkpoints source rows in `intent_source_runs`. Ranking and semantic acceptance are separate from raw retrieval. No query result implies a verified buyer or budget. `/discoveries` uses `discovery_workspace._build_run_record` for history and details.
6. HN uses official Firebase indexed feeds, not historical text search. The 28 s worker deadline enclosed a 27 s sequential item traversal, per-request DNS/network checks and repeated full workspace authorization (`permit` called `owned`, which re-entered Radar authorization). A late timeout discarded completed items. The candidate retains a smaller inner network window, bounds each read by remaining time and returns partial items and an accurate cursor if the window ends mid-scan. Removed the redundant second permissions traversal while retaining the full first authorization, job/organization/lease checks and transaction fences. Unknown coverage is no longer rendered as a measured zero. Cloud Run per-hop timings for the *historical* failures were not recorded, so the precise contribution of Neon vs network in each original timeout is unknown.
7. The old **Retry Failed Sources** control actually created a new run with a fresh UUID and full selection. It now targets the original job; successful source checkpoints are reused. Incomplete-source results now make the job retryable while retaining completed data. Final expired Discovery leases formerly fell outside the scheduler's `attempts<3` query; bounded cleanup now closes them while retaining their results. Production read-only inspection observed **five completed, four partial, zero running** jobs at inspection time. This does not disprove an earlier stale display.
8. Nine production searches span **three periods: 5 + 2 + 2**. The development grant period started `2026-11-21T07:30:37Z` and records two used searches, zero reserved. Sidebar and Billing both read `/organization/usage`, using the effective period. Radar mutations previously did not invalidate the usage query. Run/draft now invalidate that workspace's usage query. No counter, period or charging rule was edited. Full signed-in UI confirmation and cancellation/partial billing matrix remain required.
