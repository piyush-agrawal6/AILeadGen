## Account and quota model

- Schema 1016 introduces explicit billing accounts, workspace links and billing administrators. Account ID is the original primary workspace ID so existing contracts, provider metadata, invoices, usage periods, provider event deduplication and grants retain their immutable foreign keys. Billing account identity is separate from workspace context. Product access resolves the account; ICP, company profile, research, jobs and integrations still use the requesting workspace.
- Initial migration backfills **one independent account per workspace**. No automatic historical grouping by email or membership. Sole creator/owner is nominated as billing administrator; ambiguous ownership requires review. Product-wide shared-account behavior is behind `SHARED_BILLING_ACCOUNTS_ENABLED` (default false). New workspaces can explicitly select an administered account; when there is only one eligible account the new workspace can inherit it. The existing five-workspace creation safety setting is not a subscription quota.
- `scripts/attach_billing_workspace.py` is a DB-owner operator command, dry-run by default. It requires a verified common creator/sole owner, explicit target, account authority, reason, unchanged single-workspace source mapping, and absence of independent target billing history. An audit receipt records the original grant ID and expiry when applicable. A failed check must roll back the transaction. No cancel/refund/payment API is called. No change to the grant's own issue/revoke receipts.
- Metered reservations use the account anchor under a database row lock; linked-workspace operation IDs have their own namespace. Both workspaces see one period balance. AI attempts retain distinct identities, uncertain reservations and scoped settlement. Account seat capacity counts distinct active people; invitations are considered at admission. Monitor counts pool across attached workspaces. Checkout, portal, cancel and change are restricted to account administrators in the primary workspace. A linked workspace does not receive receipt URLs, a new trial or an independent checkout. Original signed provider events continue to reconcile against the original customer and contract.

## Onboarding and tenant-state audit

The main progress query and session storage were already keyed by workspace. However, profile saves populated a generic `organization-profile` key and review/advice cache keys omitted the workspace. The candidate scopes those keys and passes a broker-signed expected workspace on onboarding reads/mutations; a switched tab receives 409 before a mismatched operation. Profile responses with an unexpected workspace ID are not rendered. Website edits sever the Copilot continuation; a parent recommendation from an older saved profile version is rejected. The ICP generator now requires a saved offering. This is evidence of stale-presentation hazards, **not proof of an unauthorized tenant disclosure**. On read-only inspection both stored SyntaxWars review references belonged to SyntaxWars, and its saved website, description and positioning did not contain the PlaneByte string. This does not prove every historical response was correct.

The navigation rail has three milestones; website review is part of business setup, and activation is separate. Copilot opens on demand instead of occupying a permanent desktop column. Finishing a covered setup proceeds to ready rather than opening payment. Real source status replaces hardcoded fallback claims. Existing approved profile/ICP/research data remain server-side; unsubmitted edits still use workspace-scoped session storage and are not yet a cross-device draft facility.
